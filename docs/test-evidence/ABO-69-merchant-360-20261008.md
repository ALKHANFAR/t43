## Isolation and customer blockers

- From the new company's chat, native `ap_flow_structure` on another company's Flow `FTq62yFoPsTBvcIKFeqJk` returned `Flow not found` and did not expose its structure. This is one negative project-scope test, not exhaustive authorization coverage.
- `POST /siyadah-api/v1/integrations` with `{op:"methods",piece:"@activepieces/piece-asana"}` returned HTTP 409 `native_mcp_discovery_required` from the new company. Customer connection setup is blocked; therefore no new-customer provider connection or provider result was achieved.
- The complex build, edit, and test requests settled as `request_status:not_observed`, `work_status:unknown`, `outcome_kind:unverified` in Siyadah even when independent Activepieces readback proved a saved draft and TESTING runs. The model's prose claimed completion; the customer-visible request state did not. Product evidence needs a scoped draft/test receipt rather than upgrading this to production success.
- The new account's browser UI journey was not completed. Signup and chat were exercised through the production API, and the grant used operator consent. The end-to-end customer self-service journey and visible result remain unproven.
- A Flow-specific external MCP token and full lifecycle/authorization coverage were not tested or delivered by this probe.

## Release verdict

This proves new-account provisioning, a project grant, native MCP Flow construction, project isolation for one foreign Flow, and draft TESTING behavior. It does **not** pass general production readiness. Next release gates are native auth-schema discovery for customer tool connections, customer self-service MCP consent, scoped draft/test evidence in the UI, a real provider connection and result from a new company, and authorization/recovery coverage. PR #64 remains draft and undeployed; its local tests do not substitute for a live retest after deployment.

## Completed-branch reuse audit — 8 October 2026

The current branch already contains the project-scoped connection lifecycle and OAuth attempt handling introduced by `6936233` (and later merged through PR #61). Its connection setup originally read piece auth metadata from `GET /api/v1/pieces`. Commit `6c94a4a` deliberately replaced that single metadata read with `native_mcp_discovery_required` and added a test requiring zero REST metadata requests. Copying the old branch would reverse the native-discovery boundary without adding a native MCP auth-schema capability. No reviewed branch contains that capability.

The unmerged `ABO-66` branch (`39f5437`) reads employee Flow context through REST and gives it to chat; the current branch already has native `ap_flow_structure` and scoped `ap_get_run` access. The older live-data branch (`f2f93db`) requires fresh MCP readback for app answers. The published-outcome branch (`4528eb1`) adds tests for a published result, not a receipt for saved DRAFT plus TESTING runs. None closes the merchant probe's unknown customer-visible state without a new, narrowly scoped proof contract.

The smallest compatible implementation is an auth-schema read tool **inside Activepieces native MCP**, returning the piece version and declared auth methods/fields to the caller's project session. Siyadah can then reuse its existing `methods`, `selected`, `authValues`, OAuth and project-scoped connection code by replacing only `metadata(piece)` with a native MCP read. The Activepieces checkout here is a Docker overlay on the official 0.92.1 image, not a source fork; no MCP auth-schema tool exists in it. This audit makes no code or deployment claim for that adapter. After it exists, verify method discovery and fingerprinting, customer-owned connection creation, a provider action and readback, and the customer-visible result on a new company.
