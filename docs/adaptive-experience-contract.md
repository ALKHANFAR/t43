# Adaptive Experience: عقد العرض والتسليم

## النطاق

يستخدم الشات الرئيسي وشات الموظف حلقة DeepSeek الحالية وAPI سيادة الحالي. لا توجد طبقة اختيار أدوات جديدة ولا قالب موظف مبيعات مغلق. النموذج يختار النص أو تركيب مكونات العرض من البيانات المتاحة. حرية تعديل الموظف والخطة والأدوات والسلوك تبقى بالنص الطبيعي.

رد اختياري داخل رسالة النموذج الموجودة:

```json
{"schema_version":"1","fallback_text":"جهزت خطة للمراجعة؛ بقيت سياسة الخصم.","blocks":[{"type":"plan","title":"خطة راشد المقترحة","items":["راجع المنتجات وسياسة الأسعار","جهز العرض للمراجعة"]},{"type":"form","title":"المعلومة الناقصة","items":["سياسة الخصم"]},{"type":"suggestion","title":"إضافة اختيارية","items":["هل ترغب في مناقشة متابعة غير المستجيبين؟"]}]}
```

الأنواع: plan (تفاصيل مطوية)، form (حقول نصية مع حرية الإجابة بالشات)، table (أزواج نصية)، suggestion (اقتراح واحد مع رفض محلي). حد parser: 12000 حرف للعقد، 6 blocks، 40 items، 160 حرفًا للعنوان و2000 للعنصر. حدود العرض تحمي DOM ولا تحصر أدوات أو أقسام الشركة. رد النموذج الحالي في الخادم ما زال محدودًا بـ6000 حرف؛ العرض الذي يتجاوز ذلك قد يرجع نصًا آمنًا بدل مكونات، فلا تدّع اكتمال JSON طويل.

parser مشترك app/reply-view.js يُستخدم من lib/chat-ui.mjs في الخادم ومن المتصفح عند الرد والتاريخ. الحقول غير المعروفة تبطل العرض؛ fallback_text الصالح يعرض نصًا escaped مرة واحدة. لا model HTML/JS/CSS/URLs، ولا model action/status/employee identity. لا spread لعقد النموذج إلى API. عناصر الموظف والموافقة والتشغيل وtool_receipts من الخادم وحده، في siyResultRow الموجود.

أزرار الحقول والاقتراحات تضيف إلى صندوق الكتابة دون send أو API. الأزرار لا تثبت موافقة ولا تشغّل موظفًا. قيم الحقول وفتح التفاصيل ورفض الاقتراح تبقى عند إعادة رسم نفس الرسالة؛ لا تُنقل إلى شركة أو محادثة أخرى. إعادة تحميل الصفحة تستعيد العقد من نص التاريخ الموجود؛ قيم حقول غير مرسلة لا تحفظ في قاعدة البيانات. لا تكلفة LLM للعرض والنقر والتفاصيل. إرسال تعديل طبيعي يستدعي نموذجًا لأنه طلب جديد.

## نموذج المبيعات العملي

في بيئة اختبار معتمدة تعمل على نسخة الفرع، استخدم حساب شركة اختبار ومسار /app/chat.html الحقيقي:

1. «أبغى موظف مبيعات يتابع العملاء ويجهز عروض الأسعار، اعرض الخطة أولًا دون نشر أو إرسال». يقرأ السياق؛ يبين خطة وحقائق ناقصة؛ لا تظهر مسودة محفوظة إلا بإيصال API الموظف.
2. «سمّه راشد، خله سعودي مهني، يستخدم أدوات تناسب شغله، والخصم يرجع لي». التعديل في نفس الموظف ومعرفة الشركة؛ الأدوات يكتشفها MCP، لا يفرضها renderer.
3. «خلها أبسط» ثم «أضف متابعة غير المستجيبين كاقتراح فقط». تقل التفاصيل المرئية؛ لا تغير الحالة ولا تنفيذ تلقائيًا.
4. «جهز الاختبار على بيانات اصطناعية، لا ترسل للعملاء». اقرأ النسخة والمدخلات والأثر المتوقع؛ أي تشغيل لاحق حسب الموافقات القائمة.
5. بعد الموافقة الصريحة في بيئة QA فقط: تحقق من tenant→employee→flow→tested version→run→provider receipt. فشل أو timeout يبقي هوية الطلب ويستعلم عنه؛ لا إعادة إرسال تلقائيًا.

هذه تعليمات قبول على المسار الحقيقي، ليست موظفًا حيًا أُنشئ هنا. لا حساب QA مصادق للنسخة المعزولة ولا مفتاح DeepSeek محلي متاح أثناء التنفيذ. الإنتاج الحالي لا يحتوي هذا التغيير. لا تستخدم journey-preview كإثبات؛ هو محاكاة معلنة منفصلة.

## قياس التكلفة

chat_model_usage يتضمن company_id/request_id/conversation_id/model/model_call/observed_at_ms وtokens/cache/elapsed_ms/status. request_id يأتي من memoryRequestId الموجود؛ بعض استكمالات النظام لا تمرره، وتبقى تكلفتها غير قابلة للنسبة الدقيقة بدل تجميعها كرحلة ناجحة. استهلاك مجهول ليس صفرًا. لا نسجل محتوى المحادثة أو قيمة مفتاح.

أداة node scripts/journey-cost.mjs usage.jsonl reviewed-prices.json تجمع الرحلات وتطبق ورقة أسعار مؤرخة. الورقة تحمل model/source/valid_from/valid_until/input_uncached/input_cached/output (USD لكل مليون token). لا أسعار مفترضة في الكود. نقص usage أو cache أو هوية أو أسعار مؤرخة، أو تكرار call identity، يعطي model_cost_usd:null. تكلفة الأدوات الخارجية منفصلة؛ الناتج حساب استخدام مزود وليس تسوية فاتورة الحساب. نموذج الاستدعاء المحلي له صفر token cost عندما تكون التجربة localOnly معلنة وقائمة الاستدعاءات فارغة؛ لا تستخدم هذا لإعلان تكلفة الرحلة كلها صفرًا.

## قبول التجربة قبل النشر

عشرون طلبًا متنوعة بالعربية والإنجليزية: سؤال بسيط، إنشاء مسودة، تعديل الاسم، تغيير النبرة، تبديل أدوات، خطة معقدة، مقارنة، بيانات جدول، معلومة ناقصة، معرفة محفوظة، خلها أبسط، طلب توسيع، رفض اقتراح، قراءة فقط، طلب نشر، اختبار نسخة قديمة، فشل أداة، timeout، إعادة فتح، شركة أخرى. قيّم هل العرض مفيد وهل يستبقي القرار للمستخدم، لا مجرد صحة JSON.

قارن 100 رحلة قبل/بعد بنفس المهام والسياق: completion مثبت، أول نتيجة مفيدة، وقت الإكمال، عدد أسئلة التوضيح، model calls وtokens/cache والتكلفة، الأخطاء، وتقييم العميل. لا نتيجة مقارنة أو ضمان تكلفة/إبهار قبل إجراء التجربة. اختبارات jsdom ليست دليل شكل الجوال أو أداء متصفح حقيقي؛ Chrome/مراجعة بشرية لازمان. SSE وتحديثات delta غير منفذة في هذه الدفعة، والمسار الحالي يستعلم عن حالة الطلب.


التحقق المحلي النهائي: runtime 543، نجاح542، تخطي PostgreSQL واحد، صفر فشل؛ index28/316، lint/HTML/diff ناجحة. axe/jsdom صفر مخالفات عبر7 صفحات؛ Chrome والجوال المرئي لم يُختبرا. developer-lab/adaptive-experience-validation-20261010.json يسجل المتبقي بصراحة. هذه دفعة النموذج الأولي، لا إغلاق لمهمة UX360.
