# ABO-40: small read-only tool inventory

`pilot_discover` is an authenticated Siyadah integration operation. The server obtains the company from the session, resolves its Activepieces project, and reads three fixed Pilot pieces: Gmail, Google Calendar and Google Sheets. It neither accepts a client project ID nor connects, tests, builds or runs an action. The visual experience remains unchanged.

The result is **an inventory**, not a decision that an employee can run. `eligibleForExecution` is always false. The piece versions in `PILOT_PIECES` are from checked-in `pieces.js`; `version_drift` means the live piece differs. `no_match` means exact lookup returned no piece. The list lookup supplies a live version and action/trigger **counts**; the service then requests `/api/v1/pieces/{pieceName}?version={liveVersion}` and accepts schemas only if the detail name and version exactly match. An unavailable action/triggers collection, `aiMetadata`, classification, audience, input property details, or output schema is `unknown` and must not be filled from the marketing description. Output fields are taken only from the piece's declared `outputSchema`; that schema is a presentation contract, not provider-result proof. A connection is marked from project-owned Activepieces connection rows, and its version is compared with the live piece; it is not authorization to execute. An operation's explicit `requireAuth` takes priority over piece auth metadata. `approval` stays unknown until Siyadah policy defines it.

The connection list follows `next` cursors. Malformed or incomplete pages and any connection that lacks `scope: PROJECT` with exactly one `projectIds` entry equal to this company project fail closed; a shared project connection is not presented as company-owned. Responses omit connection secrets, auth values and defaults. All tests use synthetic provider responses. No customer connection or live provider was used. The older general connection service accepts a project ID anywhere in `projectIds`; its stricter isolation policy is separate follow-up work and is not changed by this inventory PR.

Read-only production inspection on 2026-10-01 showed the list lookup returned counts only: Gmail 0.17.0, Calendar 0.12.0, Sheets 0.17.0. The version-pinned detail GET returned action/trigger objects (11/4, 9/7, 27/4 respectively). This validates the two-request shape, not a customer connection or executable capability. Tests use synthetic schemas and must not be reported as live action proof. If the detailed response omits `actions` or `triggers`, `schemaStatus` and `status` become `unknown`; a mismatched detail name/version is rejected. Activepieces' [own issue #14596](https://github.com/activepieces/activepieces/issues/14596) documents the versioned detail GET, while the list/detail response shape was checked on the intended instance.

The official [piece schema](https://www.activepieces.com/docs/endpoints/pieces/schema) documents the actions and triggers collection and version. The [connection list API](https://www.activepieces.com/docs/endpoints/connections/list) documents project scope and cursor pagination. [AI metadata](https://www.activepieces.com/docs/build-pieces/piece-reference/ai-metadata) and [output schema](https://www.activepieces.com/docs/build-pieces/piece-reference/output-schema) are optional declarations. Activepieces [MCP search](https://www.activepieces.com/docs/mcp/tools) is a separate semantic search with honest no-match behavior; this slice makes exact piece lookups only and reports `semanticSearch: not_checked`. Project-scoped MCP access and action-specific dynamic input resolution remain later ABO-40 work.
