# ABO-40: small read-only tool inventory

`pilot_discover` is an authenticated Siyadah integration operation. The server obtains the company from the session, resolves its Activepieces project, and reads three fixed Pilot pieces: Gmail, Google Calendar and Google Sheets. It neither accepts a client project ID nor connects, tests, builds or runs an action. The visual experience remains unchanged.

The result is **an inventory**, not a decision that an employee can run. `eligibleForExecution` is always false. The piece versions in `PILOT_PIECES` are from checked-in `pieces.js`; `version_drift` means the live piece differs. `no_match` means exact lookup returned no piece. An unavailable action/triggers collection, `aiMetadata`, classification, audience, input property details, or output schema is `unknown` and must not be filled from the marketing description. Output fields are taken only from the piece's declared `outputSchema`; that schema is a presentation contract, not provider-result proof. A connection is marked from project-owned Activepieces connection rows, and its version is compared with the live piece; it is not authorization to execute. `approval` stays unknown until Siyadah policy defines it.

The connection list follows `next` cursors. Malformed or incomplete pages and any connection that lacks `scope: PROJECT` or the exact project ID fail closed. Responses omit connection secrets, auth values and defaults. All tests use synthetic provider responses. No customer connection or live provider was used.

The existing `/api/v1/pieces?searchQuery=` lookup used by Siyadah may return a summary rather than detailed operations on a given deployment. This has **not** been verified against the production instance. If `actions` or `triggers` is absent, the result is `unknown`; the test fixture with both collections demonstrates parsing only and is not live proof. Before treating this inventory as a planning input, read back one real piece from the intended Activepieces instance and verify that its declared operation schemas are present, or use the documented MCP `ap_get_piece_props` through a project-scoped context.

The official [piece schema](https://www.activepieces.com/docs/endpoints/pieces/schema) documents the actions and triggers collection and version. The [connection list API](https://www.activepieces.com/docs/endpoints/connections/list) documents project scope and cursor pagination. [AI metadata](https://www.activepieces.com/docs/build-pieces/piece-reference/ai-metadata) and [output schema](https://www.activepieces.com/docs/build-pieces/piece-reference/output-schema) are optional declarations. Activepieces [MCP search](https://www.activepieces.com/docs/mcp/tools) is a separate semantic search with honest no-match behavior; this slice makes exact piece lookups only and reports `semanticSearch: not_checked`. Project-scoped MCP access and action-specific dynamic input resolution remain later ABO-40 work.
